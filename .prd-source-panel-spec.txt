这份文档解决的问题：Plugin 作为右侧工具栏入口，点击后展开 Panel。Panel 内部如果承载文件、画布、表单、预览、任务、详情、技能等多种功能，应该如何抽象布局，而不是把功能按钮堆成一锅乱炖。

1. 先纠正一个关键心智
Header、View Switcher、Command Bar、Content Body、Context Action 这 5 层，不是必须从上到下排布的 UI 横条。
正确理解：这 5 层是信息职责，不是固定排版。不同工作区模板应该重新组织这些职责，让它们长在最适合当前任务的位置。

外壳统一，内部变化。右侧展开的 Panel 应该有统一外壳，保证用户知道当前打开的是哪个插件、当前对象是什么、状态如何、如何关闭。但 Panel 内部不应该强行套同一个模板。
按工作类型选容器，不按功能数量堆按钮。当一个 Plugin 里有很多能力时，不要先问“按钮放哪里”，也不要先选具体模板。第一步只判断用户此刻主要是在 Browse（寻找和选择）、Work（持续操作），还是 Submit（填写并确认）。母版确定后，再到第 4 章选择具体界面模板。
行为母版

用户此刻在做什么

判断信号

Browse

寻找、筛选、比较和选择对象

重点是“我该选哪个对象”

Work

在一个空间中持续编辑、操作或审阅

重点是“我要继续把东西做完”

Submit

填写参数、理解影响并确认一次动作

重点是“我是否确认让这件事发生”

3. 【先读】三种行为母版：先判断用户正在做什么
先纠正关系：这三种母版不是把七种模板重新分成三个下级目录，也不是 Plugin 的三种类型。它们回答的是“用户此刻主要在找东西、做东西，还是提交一次动作”；七种模板回答的是“这个阶段具体需要什么界面结构”。因此二者是交叉关系，一个 Plugin 会随着任务阶段切换母版和模板。
3.1 浏览型容器：从集合中找到并选择对象
判断标准：用户此刻最重要的任务是缩小范围、比较对象、选中一个对象，再对它执行动作。
3.2 工作型容器：在主工作区里持续操作
判断标准：用户大部分时间都在画布、时间线、编辑器或预览主体里工作，工具和属性只负责辅助。
3.3 提交型容器：填写参数并做一次明确决策
判断标准：用户需要提交一组参数，且提交动作可能产生费用、权限变化、发布或其他明确后果。
4. 七种具体界面模板：在母版判断后选择
不要把它理解成一棵“3 个母版 → 7 个子模板”的分类树。三种母版和七种模板来自不同观察角度，因此只能做交叉映射，不能强行一一归类。

4.0 先看懂：Plugin、母版、模板是三个层级
层级

它回答什么问题

例子

Plugin

这是哪个领域的完整工作包？

视频创作、PPT、文件管理、应用部署

三种行为母版

用户此刻主要在做什么？

Browse 找和选、Work 持续操作、Submit 填写和确认

七种界面模板

这个阶段具体需要什么界面结构？

对象列表、画布、表单、预览、任务监控等

正确的使用方式：先把一个 Plugin 拆成任务阶段，再判断每个阶段属于 Browse、Work 还是 Submit，最后为该阶段选择具体模板。一个 Plugin 往往会连续使用多个母版和模板。
例如视频创作：挑素材（Browse → Object Browser）→ 编排视频（Work → Canvas Workspace）→ 提交渲染（Submit → Form Flow）→ 等待执行（跨阶段过程态 → Task Monitor）→ 查看成片（结果态 → Preview Workspace）。
4.0.1 七种模板与三种母版的交叉关系
具体模板

常见母版关系

为什么不能硬塞进一个类别

Object Browser

主要对应 Browse

用于从集合中查找、比较和选择对象。

Canvas Workspace

主要对应 Work

用于在画布、时间线或编辑器里持续操作。

Form Flow

主要对应 Submit

用于填写参数、理解影响并确认一次动作。

Object Inspector

附着于 Browse 或 Work

它是对象详情二级页，不是独立的行为母版。

Preview Workspace

可附着于 Browse 或 Work

它常是结果页，也可能成为持续审阅和反馈的工作区。

Task Monitor

跨母版的过程状态

它通常出现在提交或执行之后，负责进度、日志、错误与接管。

Command Picker

跨母版的入口路由

它先帮助用户选择要做什么，之后可能进入 Browse、Work 或 Submit。

一句话记忆：三种母版是“用户正在干什么”，七种模板是“这一刻界面长什么样”，Plugin 是“整段工作属于哪个业务领域”。

4.1 Object Browser：对象浏览容器
适合：文件、记忆、素材库、任务列表、文档列表。
核心任务：找对象、选对象、把对象交给 Agent 或打开。
按钮归置：切换内容集合放顶部 Tab；搜索、新建、导入、筛选放 Command Row；引用给 Agent、打开、更多跟随选中对象出现。
4.2 Canvas Workspace：画布工作区容器
适合：视频时间线、白板、流程编排、网页可视编辑、设计稿审查。
核心任务：在空间里操作对象，并把局部选区交给 Agent。
按钮归置：画布工具放工具条；对象属性和 Agent 动作跟随选区；全屏和打开大画布放在工具条或底部动作区。
4.3 Form Flow：表单流程容器
适合：授权、发布设置、生成参数、创建任务、审批确认。
核心任务：让用户安全、明确地提交一组参数。
按钮归置：字段控件放字段旁边；取消和确认固定底部；风险提示靠近确认按钮；不要在顶部塞搜索、新建、筛选。
4.4 Preview Workspace：预览工作区容器
适合：网页预览、PDF、图片、视频、生成结果、文档预览。
核心任务：看结果、定位问题、把结果或片段交给 Agent。
按钮归置：顶部放缩放、刷新、适配、打开新窗口；底部放引用、总结、下载。预览主体要占最大空间。
4.5 Task Monitor：任务监控容器
适合：后台任务、视频渲染、批量生成、自动化流程、运行日志。
核心任务：告诉用户现在发生了什么、卡在哪里、能不能接管。
按钮归置：顶部放状态筛选；任务卡片内放取消、重试、查看日志；错误区域放引用错误给 Agent。
4.6 Object Inspector：对象详情容器
适合：文件详情、素材详情、镜头详情、日程详情、权限详情。
核心任务：解释一个对象，并提供对象级操作。
按钮归置：主操作是引用给 Agent、打开；重命名、移动、删除放更多。Object Inspector 通常不是一级入口，而是从列表、画布、预览中选中对象后出现。
4.7 Command Picker：技能选择容器
适合：插件里有很多技能或动作，例如生成图片、发邮件、建任务、跑检查。
核心任务：选择一个动作，并进入快速配置或直接执行。
按钮归置：搜索技能放顶部；推荐动作靠前；全部技能按领域或任务类型分组；点击技能后进入表单流程、任务监控或结果预览。

6. 落到当前右侧 Plugin 工具栏形态
- 右侧竖栏：只放 Plugin 或高层 Panel 入口，不放细碎功能。
- 展开面板：使用统一 Panel Shell。
- Panel 内部：由具体 Plugin 选择容器模板。
- 一个 Plugin 可以有多个一级视图，但一级视图不超过 5 个。
- 所有模板都必须支持“引用给 Agent”或“让 Agent 处理”的上下文动作。

选中镜头后：引用给 Agent / 重新生成 / 更多7. 设计评审 Checklist
这个 Panel 当前视图属于哪一种容器模板？用户是在找对象、操作对象、提交参数、看结果、看进度、看详情，还是选择技能？顶部按钮是否都是全局工具？有没有把对象级按钮错误放到顶部？选中对象后，是否明确出现“引用给 Agent”或“让 Agent 处理”？危险操作是否被收进确认流程，而不是常驻暴露？如果是画布或预览，主体内容是否占据最大空间？如果是表单，底部确认区是否稳定可见？这个 Panel 是否仍然和左侧聊天发生关系，而不是变成独立后台页面？8. 最后一句话
不要设计一个万能 Panel。要设计一套容器模板系统。统一的是外壳、状态和与 Agent 的引用关系；变化的是中间工作区的容器形态。
