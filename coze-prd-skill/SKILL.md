# Coze PRD 规范

## 目标

把零散需求整理成可评审、可研发、可验收、可追踪的产品需求文档。文档必须让产品、设计、研发、测试、数据、安全和法务能快速找到与自己相关的信息。

本规范提炼自一份 Coze 项目协作 PRD 的稳定写法，不照搬其中的项目名称、功能结论、人员、链接、分支或指标。

## 执行顺序

1. 识别任务：新建 PRD、改写现有 PRD、补齐章节或评审 PRD。
2. 收集已有事实：业务背景、用户问题、目标、范围、方案、端、角色、状态、指标、设计稿、依赖和发布要求。
3. 将缺失信息分成两类：
   - 阻断方案或验收的关键缺口：明确列为“待确认”，必要时向用户提问。
   - 不阻断结构化表达的缺口：保留 `待定`，禁止编造。
4. 按 `references/prd-template.md` 组织正文。
5. 按 `references/style-guide.md` 统一排版和语言。
6. 按 `references/review-checklist.md` 自检；发现缺口时在交付末尾列出“待确认事项”。

## 核心写作规则

### 先结论，后证据

每个章节先用一段话交代结论，再用表格承载多维信息。不要让读者从长篇背景中猜目标或范围。

### 从用户动作写到验收

功能方案优先使用四列表：

| 用户场景 / 用户操作 | 系统响应 | 关键状态 / 文案 / 兜底 | 评审口径 / 验收点 |
| --- | --- | --- | --- |

每一行形成完整闭环：谁在什么场景做什么，系统如何响应，出现哪些状态或异常，最终如何判定通过。

### 显式写边界

必须区分：

- 本期做 / 本期不做 / 后续计划。
- 原型现状 / 生产化要求。
- 已确认事实 / 判断 / 待确认事项。
- 正常态 / 空态 / 加载态 / 成功 / 失败 / 失效 / 无权限。
- 管理员、协作者、普通用户、Agent 等角色的查看权、发起权和关键操作权。
- Web、Server、App、桌面端等端的覆盖状态。

状态值优先使用统一枚举：`resolved`、`follow_up`、`out_of_scope`、`pending`。首次出现时用中文解释。

### 文案可直接验收

界面文案使用中文引号，例如：“帮我更新”。写清触发时机、展示位置、角色差异和失败兜底，避免只写“优化体验”“友好提示”“支持相关能力”。

### 不编造

未知的指标目标、负责人、排期、技术结论、合规结论和链接写 `待定` 或列入待确认。不得为了让文档看起来完整而补造事实。

## 默认文档层级

- 文档标题：`[PRD] {需求名称}`
- 文首信息区：关联任务、设计稿、分支、预览、发布状态等；没有的信息省略或标记待定。
- 修改记录：日期、修改人、修改记录。
- 二级章节：需求背景、产品方案、核心指标、项目管理字段、附录。
- 三级章节：问题、收益、各功能、权限、端覆盖、数据、合规、发布等具体主题。
- 不使用超过四级的标题；复杂关系改用表格或列表。

## 排版规则

- 一段只表达一个结论；段落通常为 1–4 句。
- 表格用于比较、矩阵、状态机、角色权限、端覆盖、埋点和验收，不用于单句装饰。
- 无序列表用于并列规则；有序列表用于必须按顺序执行的流程。
- 行内代码用于事件名、状态枚举、文件名、分支、环境变量和命令。
- 链接使用有意义的名称，不用裸长链接破坏阅读。
- 提示块只承载关键规则：黄色/警告表示强约束或风险，蓝色/信息表示语义解释，橙色/人员表示需协作处理。普通内容不要滥用提示块。
- 加粗只突出字段名、结论词或风险词，不整段加粗。

## 输出约定

### 新建或重写

先输出完整 PRD，再输出“待确认事项”。如果用户指定飞书文档，可将模板转换为飞书 XML；如果未指定，默认输出 Markdown。

### 评审

按严重级别输出问题：

1. 阻断：无法研发、上线或验收。
2. 重要：状态、权限、异常、数据或范围存在明显缺口。
3. 建议：结构、排版或措辞可以改善。

每条问题必须包含：所在章节、问题、影响、建议改法。随后给出可直接替换的文本或表格。

### 信息不足

不要只回复“请补充更多信息”。先用现有信息搭好文档骨架，将未知内容标记为 `待定`，再集中提出最少量的关键问题。
