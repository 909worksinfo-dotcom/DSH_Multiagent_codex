# Agent Note：可审阅协作方案确认

状态：已实现

[English](2026-08-29-reviewed-collaboration-plan-confirmation.md) | 中文

## 问题

独立多智能体入口此前把提交任务直接视为对任务画像、规划、专家组队与 Lead 启动的一次性授权，用户无法在模型工作开始前检查任务 DAG、执行 Agent 和已挂载能力，后续修改要求也无法阻止原团队开始执行

## 决策

产品创建边界现在拆分为两个持久化命令。`collaboration.create` 会创建 Lead 持有的 TeamRun，并提交 Task Profile、精确 roster 计划、Team Charter、任务 DAG、计划执行席位和任务选中的能力绑定，但会让运行保持在 `planning`，不创建专家成员、不物化任务、不向 Lead 发送执行提示。`collaboration.confirm` 使用匹配的 request identity 确认方案，按精确 roster 创建专家，物化并分配 Charter 任务和质量门，激活 TeamRun，然后才提交现有 Lead 执行提示

独立入口和方案审阅界面固定使用中文产品文案。审阅页会展示完整目标、根据依赖推导的串并行阶段、每项任务计划执行的专家名称，以及每名计划专家的职责、预置、已挂载技能和插件。用户可确认精确方案、返回修改任务目标、输入自由文本修改要求，也可通过 GUI 编辑每名专家的本地技能。编辑器会查询当前 Lead Session 中模型可调用的技能目录，支持本地搜索，在达到当前专家技能下限时禁止继续删除，并在选中内容尚未应用时禁止确认。应用技能修改会携带每名专家的精确替换技能创建新的不可变计划记录，通过既有规划器和 preset 解析验证全部选中技能，然后取消旧草案。替代方案创建或验证失败时，当前已审阅草案仍然可用

右侧协作面板只会在用户确认后打开，现有执行路由、并行阶段准入、完成证据、公开讨论、模型 provider、审批策略和执行消息折叠保持不变

目录恢复会先通过持久化 profile 标记发现实时 Lead，再对每个运行执行严格回放。历史运行无法满足当前回放合同时，只有在至少一个健康运行仍可见的情况下才会单独省略该历史项。全部不兼容时目录仍会返回明确失败，不会伪装为没有协作历史

## 验证

UI 组件测试证明确认前会展示三名或更多专家及其分配任务，不会提前出现执行会话，确认后会进入现有 Lead 视图，英文系统 locale 不会泄漏到入口，自由文本修改会替换草案且不会自动确认。测试还会删除一项已挂载技能，搜索并添加可用替代技能，在 GUI 选择尚未应用时禁止确认，并验证提交给新审阅方案的每专家精确替换要求

运行时与 carrier 测试覆盖新的类型化确认 RPC、`createRun` 期间不发送 Lead prompt、审阅阶段技能查询中的模型可调用过滤、精确 Charter 负责席位投影、`confirmRun` 期间的激活与 prompt 准入、prompt 准入需要重试时保留 active 状态，以及不兼容历史运行旁仍保持健康目录可见性。真实 TeamOrchestrator 组合测试证明 `create` 保持成员与任务存储为空，审阅技能替换会在发布前完成解析，`form` 才会按精确已审阅方案完成组队与物化

## 已考虑的替代方案

**只在浏览器中生成临时方案。** 已拒绝，因为它可能与 Host 后续执行的 roster、任务 DAG 和能力绑定不一致

**审阅前先创建专家，只延后 Lead prompt。** 已拒绝，因为用户批准团队配置前已经产生专家会话和 provider 副作用

**每次修改时就地改写现有计划。** 已拒绝，因为这会破坏不可变审计并让重试语义模糊

**只在浏览器中显示可编辑技能列表并在确认时直接传递。** 已拒绝，因为可见列表可能偏离 Host 持久计划，也会绕过 preset 级技能解析

## 影响

启动协作现在需要一次明确确认并增加一个类型化 RPC。计划草案可持久且可恢复，已取消的修订保留审计，审批前不会创建专家或启动模型执行。GUI 技能修改会增加一次只读技能目录请求和一次替代规划事务，但精确已审阅绑定仍是组队与恢复使用的唯一来源。UI 增加一个信息完整但有界的确认界面，active TeamRun 行为与现有协作执行保持兼容
