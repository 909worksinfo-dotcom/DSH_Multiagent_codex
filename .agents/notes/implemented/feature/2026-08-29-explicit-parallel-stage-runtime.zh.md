# Agent Note：明确并行阶段运行时

状态：已实现

[English](2026-08-29-explicit-parallel-stage-runtime.md) | 中文

## 问题

Team Charter 已经把依赖层标为串行或并行，但运行时始终只把一份执行接力交给一名专家，因此 UI 可能展示并行阶段，模型回合却仍然串行运行

## 决策

串行阶段保留既有单消息交接和发送者空闲后再投递的行为。只有 committed mode 为 `parallel` 的 Charter 阶段可以使用新增的 Lead-only `collaboration_parallel_followup` 工具；当该阶段至少有两个就绪任务时，单条串行任务路由会被拒绝

Lead 会原子发布每个不同预分配专家的一条任务消息。运行时并发启动全部专家 inbox，只为成功准入的专家授予执行许可，并在所有已准入专家回交完全相同的任务前阻塞 Lead 和非参与成员。最后一个回交会关闭一次 barrier，只唤醒 Lead 一次，并携带所有公开回交摘要与初始准入失败

公开批次使用一个稳定的并行 thread。live router recovery 会从持久消息重建未完成参与者与已完成回交，不修改历史事件

已准入的参与者后续成为持久化 failed 成员时，会被解算为失败的批次结果，不再永久占有 barrier。非模型 runtime controller 会在汇合唤醒 Lead 前，先尝试在同一计划 protocol slot 中执行一次幂等补位。Lead 会收到全部成功回交与失败任务证据，再把未完成工作显式重新分配给活跃补位专家，不得把该阶段报告为已完成

## 验证

测试证明两个 inbox 中任意一个完成前全部并发准入、最终只唤醒 Lead 一次、明确串行阶段拒绝并行、就绪并行阶段不会意外逐条派发、部分准入失败处理、已准入参与者失败时释放执行权并调用 runtime 补位、公开批次原子回滚，以及既有串行路由行为保持不变

## 已考虑的替代方案

**只把并行标签保留为依赖元数据。** 这会保留旧路由器，但向用户展示运行时并未兑现的并行承诺

**重复调用串行 follow-up 工具。** 第一次调用会结束 Lead 回合并转移唯一接力，因此后续调用无法并发启动，也没有确定性 join barrier

**并发运行所有就绪任务。** 就绪本身不授权并行执行，committed 串行阶段可能表达必须保留既有单接收者路径的顺序或评审意图

## 影响

当多个已分配专家同时就绪时，明确并行阶段现在可以缩短执行耗时；串行阶段和只剩一个任务的情况仍保留原路径。适配器新增一个 schema、一个持久批次 thread，以及一个可从公开消息重建的进程内 barrier。Lead 必须先处理汇报的 inbox 准入失败，剩余任务才能完成
