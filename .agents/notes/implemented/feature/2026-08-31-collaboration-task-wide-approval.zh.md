# Agent Note：协作任务级授权

状态：已实现

[English](2026-08-31-collaboration-task-wide-approval.md) | 中文

## 问题

日常审批服务已经支持 `allowed-for-turn`，但该授权有意限制在单个 Agent 的一次轮次内，并且只匹配同一工具名称与消费方提供的 task key。多智能体 TeamRun 可能同时存在多个专家会话、不同工具、并行等待问题和后续轮次，因此如果直接把原结果展示为整项任务授权，团队仍会再次卡住，界面也会夸大实际权限范围

## 决策

核心 `ApprovalOutcome` 保持不变。Web 应答契约增加仅供协作模式使用的 `allowed-for-task`，`approval/requested` 增加可选 `collaborationRunId`。Host 只有在确认请求者属于当前活跃 TeamRun 且任务处于非终态执行状态后才会输出该字段

ApiProxy 按精确 TeamRun id 维护一组进程内授权。带协作范围的等待问题收到 `allowed-for-task` 后，Host 会重新校验该请求的成员身份、记录授权，并把同一任务已经等待的全部问题按 `allowed-once` 统一放行。授权之后才到达的请求也会在发布可回答帧之前按 `allowed-once` 处理，因此 ApprovalService 仍会为每项操作写入完整的 `approval/asked` 与 `approval/decided` 审计事件对

协作面板只在等待请求的 `collaborationRunId` 与当前展示任务一致时显示新操作。原有 `allowed-for-turn` 继续作为范围更窄的“当前 Agent 允许”。专家进入待审批状态时，面板会请求布局所有者打开已收起的协作栏；活跃任务没有待审批时则保持用户当前的面板状态。日常会话界面与无协作范围的审批请求保持原行为

授权有意只保存在内存中。Host 重启后会再次询问，终态任务或失效成员不能建立授权，范围不匹配或伪造的任务级应答会以拒绝方式关闭

## 验证

Host 探针测试在同一任务内创建两个并行专家审批，只对其中一个选择任务级授权，证明两个等待请求都会落定；随后证明另一个专家使用不同工具时不再产生新问题，同时证明无关日常会话仍然出现审批并可被拒绝

客户端测试证明 TeamRun 范围经过 mux 投影后仍然保留，精确的任务级结果能够到达 `/api/respond`，按钮会在当前任务显示，并在 Host 未提供协作范围时保持隐藏。测试同时证明待审批专家会打开已收起的协作栏，没有待审批的活跃任务不会打开。Schema 测试覆盖新的可选帧字段与客户端可回答值

## 考虑过的替代方案

**原样复用 `allowed-for-turn`。** 该方案只能授权单个 Agent 轮次内的匹配操作，无法覆盖并行专家和后续专家

**把 `allowed-for-task` 加入核心 `ApprovalOutcome`。** 该方案会强迫全部审批消费方理解 TeamRun 所有权，而目前只有 Web 协作网关具备该上下文

**把授权持久化到 TeamRun 日志。** 该方案能够跨重启保留授权，但会引入 Demo 当前并不需要的持久高权限与撤销契约。进程内范围更安全，也与现有临时授权姿态一致

## 影响

用户一次明确操作即可放行一个运行中多智能体任务的当前与后续全部审批，同时保留每项操作的审计事件。日常会话语义、核心工具消费方、会话审批策略、模型选择、沙箱模式与历史 TeamRun 回放均保持不变
