# Agent Note: 审阅方案要求强制执行

Status: implemented

[English](2026-08-29-reviewed-plan-requirement-enforcement.md) | 中文

## Problem

协作方案确认页此前通过把自由文本修改追加到任务目标并再次生成确定性方案来接受修改。类似“每个专家挂载三个技能”和“阶段 1 的两个任务改为串行”的明确结构要求因此只出现在文本中，没有约束技能绑定或任务依赖。连续修改还会重复嵌套多个调整要求标题，并把这些标题带入任务描述

这会形成错误确认风险，因为用户可能确认一份专家配置和执行阶段均与修改要求矛盾的持久章程

## Decision

审阅目标现在只保留一个累计调整要求区块。Profiler 会先将历史重复标题规整为一个区块，再把原始任务与累计要求分离，并把可执行的技能数量下限和阶段模式要求解析到持久 Task Profile

阶段串行要求会在任务分配前转化为真实依赖，因此预览分组、持久事件回放和运行时 ready 状态使用同一份标准 DAG。精确的阶段与任务要求会在阶段变换前绑定到一基引用的任务，追加到该任务的可见描述，并在要求飞书文档等已知交付物时转换为能力与资源信号。阶段与任务不匹配时规划会直接失败，不会修改其他步骤

每位专家的技能下限只统计不可变本地技能，以及状态为 `loaded` 或 `connected` 的任务级市场能力。任一专家未达到用户要求时，规划会在发布可审阅方案前显式失败；待授权能力不计入已挂载技能

当前专家蓝图会从既有 standard preset 挂载三个可执行本地技能。本次不修改任何 Skill 实现或 Plugin 内容

## Verification

回归测试证明原始故障输入会生成四个串行阶段、任务描述不再包含调整要求文本、“阶段3 04任务需要最终产出飞书文档”只会作用于精确最终任务、不一致的阶段与任务引用会被拒绝、持久事件回放可正确验证该拓扑，并且只有两个可执行技能时不会持久化方案。UI 回归测试连续提交两次修改，证明最终只保留一个累计调整要求标题

受影响的协作测试、Host 与 Client 类型检查、定向静态检查、完整网页构建和本地浏览器运行共同验证生产装配以及方案审阅到确认执行的边界

## Alternatives considered

**继续依赖关键词相关度** 不予采用，因为相关度只能调整专家排序，不能证明技能数量和执行模式满足要求

**把修改要求仅作为提示文本展示** 不予采用，因为确认页代表即将提交的执行合同

**把待授权市场能力计入已挂载技能** 不予采用，因为这类能力在授权前不能执行，会导致“已挂载”标签失真

**改写已有规划事件** 不予采用，因为持久审阅草稿是不可变审计记录。重新生成会创建一份修正后的新方案，并保留已取消草稿

## Consequences

已支持的结构修改现在是可观察的执行约束，不再只是提示词装饰。用户确认前，预览阶段、运行时任务就绪关系和专家技能数量保持一致。能力不足会返回明确规划失败，而不是展示表面成功但违反要求的方案
