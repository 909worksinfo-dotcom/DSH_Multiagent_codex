# Agent Note: 恢复运行中的协作任务并避免依赖任务被误判停滞

Status: implemented

[English](2026-08-30-collaboration-run-recovery-and-stall-readiness.md) | 中文

## 问题

控制器会把所有长时间保持 pending 的任务都认定为停滞，包括声明的前置任务尚未完成的后续任务。因此在前一个并行阶段仍在执行时，合法的后续阶段就可能把整个任务错误标记为阻塞

页面刷新后，中间协作工作区只会恢复尚未确认的规划草案，右侧面板则盲目选择目录第一项。运行中的任务可能从中间区域消失，而更新但已取消的草案会占用右侧面板，用户看到的就是协作任务未启动且面板似乎空白

目录启动时会把所有历史任务的时间线作为一个全有或全无的批次加载。已有 85 条持久化任务时，请求洪峰会在当前任务显示前冲断浏览器连接。右侧面板还会使用 sessions 服务读取审批投影，却没有声明该依赖，导致冷启动渲染持续抛错

Host 重启后，已经持久化的并行回交消息可能仍然存在，但对应专家 Agent 的进程内实例已经消失。路由恢复会把这种情况误判成团队成员失效，并拒绝 Lead 后续使用全部协作工具。同一批次中尚未完成的专家也可能继续被记录为活动状态，却没有实际运行中的回合来完成任务

## 决策

停滞检测现在只考虑正在执行的任务，以及所有声明前置任务均已完成的 pending 任务。仍被依赖阻塞的任务保持待执行，不再降低控制器健康度

客户端恢复中间工作区时，会按创建时间选择最新的未终态协作任务。右侧面板使用相同的确定性排序，选择最新且未取消的任务

恢复运行中的任务时只自动打开一次右侧面板。活动任务工作区同时提供明确的打开面板操作，用户手动收起后可随时恢复

浏览器现在按时间倒序请求最近 20 个 TeamRun 的恢复窗口。冷启动发现先按创建时间读取轻量持久化元数据，达到窗口上限后停止，不再回放每个历史会话。目录刷新随后只为最新可见任务与最新活动任务加载时间线，把启动扇出限制在最多两条历史。选中任务后，右侧面板轮询只读取该精确任务，不再重复扫描目录。相关时间线暂时不可用时会保留最后一次正确投影。界面插件现在显式声明 sessions 依赖，同时继续按专家隔离审批读取，作为最后一道故障边界

并行路由恢复现在会直接信任专家已经持久化的回交结果，不再要求该专家仍存在于进程内存中。仍在真实运行的专家保持执行权；缺失或空闲且尚未回交的专家则依据原始任务消息与任务记录重建完全一致的私有执行许可，并且只重新派发对应的未完成任务一次，之后再完成并行汇合

## 备选方案

**提高停滞阈值。** 不予采用，因为这只会延迟同一个误报，不会真正尊重任务就绪条件

**只在组件状态中保留所选任务。** 不予采用，因为组件状态会在刷新后丢失，也无法正确处理已取消的替换草案

**每次目录更新都重新打开面板。** 不予采用，因为这会覆盖用户主动收起面板的选择，并重新引入可见的面板不稳定

## 影响

并行工作可以继续执行，不会被后续依赖阶段误判为整体阻塞。刷新应用后会恢复最新的活动任务及其面板，已完成的历史任务仍可在面板中查看，但不会意外替换中间的新任务入口

历史任务增长不再导致恢复过程扫描并加载全部旧任务。当前界面保留最近 20 个可恢复任务，持久化存储与 Host API 的无上限默认能力保持不变。审批投影缺失或暂时不可用也不再导致面板崩溃

进程重启不再把有效的并行回交结果误报成成员缺失。已完成贡献不会重复执行，尚未完成的冷专家会恢复其原定任务，Lead 只会在恢复批次真正汇合后继续推进
