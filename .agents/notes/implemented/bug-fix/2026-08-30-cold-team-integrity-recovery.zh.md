# Agent Note: 在实时与冷恢复协作任务中补齐空缺专家席位

Status: implemented

[English](2026-08-30-cold-team-integrity-recovery.md) | 中文

## 问题

专家在串行交接或等待审批期间失败后，活跃 TeamRun 可能低于已提交 roster 的人数。并行批次恢复可以释放自身屏障，但串行 owner 失败后会继续占有执行权，冷恢复还可能在专家 child Agent 就绪前先恢复 Lead。页面因此显示团队不完整，恢复回调可能完全没有运行，也可能在读取尚未恢复的参与者时抛错

## 决策

协作路由器现在会在重建串行或并行路由状态之前，根据持久化 TeamRun membership 发起一次有界的同席位补位。操作以 run 和 protocol slot 为键，重复事件不会创建重复补位尝试。原失败记录保持不可变，未完成任务继续保持未完成，成功补位会在同一 protocol slot 增加一个新的 active attempt

如果失败专家持有串行执行权，路由器会把执行权归还 Lead。补位完成后，Lead 会收到明确指令，要求刷新任务并把仍指向失败成员的未完成任务重新分配。并行批次继续使用原有的汇合通知，不会收到重复恢复唤醒

冷启动现在会在每个 Agent 到达后重新尝试协调，因为持久化 TeamRun membership 可能晚于第一次 `agent/created` 回调才可读取。缺失 child Agent 时会延迟路由重建，不再导致网页进程退出。团队级席位补位不依赖路由重建，因此可以先恢复已提交的活跃团队人数

## 备选方案

**有专家失败时隐藏完整性警告。** 不予采用，因为团队仍不完整，未完成工作仍可能被错误声明成功

**把失败成员原地改回 active。** 不予采用，因为这会销毁失败证据，导致超时和 provider 事故无法审计

**每次事件都在没有席位键的情况下重试补位。** 不予采用，因为重复 Session 事件和冷启动回调可能创建无界的重复专家

## 影响

活跃团队现在可以在串行、并行、实时和冷启动路径中恢复已提交的空缺席位，同时保留原失败记录。Lead 仍必须先重新分配未完成任务的 owner 才能继续执行。如果补位本身失败，任务会继续以可见的不完整状态存在，无法通过多智能体完成门禁
